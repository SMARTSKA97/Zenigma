# Practice levels

Every practice track (a game, or a kind of a game) has levels that are generated by `tools/generators/puzzles` and shipped inside the apps and the API, so a solution can be checked against the exact level a player was given.

## How they are stored

- `tools/generators/puzzles/level-counts.json` says how many levels each track has. It is the one place to change.
- `node build-levels.mjs` writes **packs of 1000 levels**: `apps/web/public/levels/<track>-<n>.json` (fetched by the app when a player reaches that pack, cached for offline play) and the same files embedded in the API (`apps/api/.../Games/Puzzles/levels`, loaded the first time one of their levels is needed). `counts.json` and `apps/web/src/app/games/level-counts.data.ts` carry the counts.
- Levels never change once they exist: level *n* of a track is generated from the seed `zenigma-practice:<track>:<n>`. Building again only generates the levels that are missing.
- `node build-levels.mjs --all` throws everything away and generates every level again (slow: Zip's hardest levels take seconds each).
- `node build-levels.mjs --verify` is what CI runs: it checks every pack is complete and regenerates a sample (every 40th level and the last 10 of each track) to prove the shipped levels still match the generators.

## Adding levels every week (only where players are close to the end)

A track grows by **100 levels** at a time, and only when a player is within 100 levels of its end.

1. The `Level reach` workflow (`.github/workflows/level-reach.yml`, Mondays 06:30 IST) runs `reach.sql` against the production database and commits `tools/generators/puzzles/reach.csv`: one line per track, `track,furthest level any player has solved`. No player data.
2. The weekly growth task runs `node grow-levels.mjs --reach tools/generators/puzzles/reach.csv`. Tracks nobody is near stay as they are. With nobody near an end, nothing is generated that week.
3. It then runs the tests, pushes a branch, waits for CI and merges to `main`.

`node grow-levels.mjs [amount] [--reach file] [--margin 100] [track-prefix ...]`: without `--reach` every matching track grows (a manual top-up). The last pack of a track may hold fewer than 1000 levels while it fills; existing levels never change when a pack grows.

Difficulty: most tracks reach their hardest setting around level 500 and then repeat the hardest zone-of-ten ramp (easy to hard inside each zone of ten). The Sudoku tiers (Easy to Insane) ramp inside their own clue range.

## Growth and cost

Growth is driven by players now, so the repository only grows where levels are actually being used (100 levels is about 12 KB a track, twice). The plan below is still the answer if it ever gets big. The plan, to start when the repo passes about 300 MB or a clone takes too long:

1. Keep the newest packs of each track in git. Publish older packs as GitHub release assets (or object storage) named `<track>-<n>.json`, and delete them from git history going forward.
2. The app already fetches a pack only when a player reaches it, so it would fetch old packs from the asset URL instead (the base URL goes in `environment.ts`; the service worker and the Android cache keep working the same way).
3. The API only needs a pack when someone submits a level in it, so it can fetch and memoise it the same way.
4. `--verify` keeps working from the assets in CI.

The Docker build context is `apps/api`, so the two copies cannot be shared as a single folder without changing the build.

The weekly job itself is a scheduled task, not a workflow, so it has no hard time limit in the repository. Generation takes about 10 minutes for the Sudoku kinds and the hardest Zip tiers; if a run nears the task's limit, split it by passing track names (`node grow-levels.mjs sudoku`, then `zip`, then the rest) in separate runs.

## Tracks

`<queens|tango|zip|patches>-classic-<easy|medium|hard|challenging|insane>`, `sudoku-<classic|mini>-<easy|medium|hard|challenging|insane>`, `sudoku-diagonal`, `sudoku-knight`, `sudoku-windoku`, `sudoku-disjoint`, and the rule kinds `sudoku-<killer|thermo|jigsaw|arrow|sandwich|consecutive|even-odd>`.

The tiers of the logic games slice one hardness scale (`TIER_RANGE` in `games.mjs`), so each tier has its own 1000+ levels and its own map. The weekly job therefore grows about 40 tracks by 1000 levels each; watch the repo size and the job's run time (see `docs/IDEAS.md`, Engineering and growth).

To add a kind: add its generator case in `games.mjs` (`practiceLevel`), list it in `TRACKS` and `level-counts.json`, add it to `PuzzleRules.Tracks` (API) and to `VARIANTS` in `catalog.ts`, then run `node build-levels.mjs <track>` and `node gen-vectors.mjs`.
